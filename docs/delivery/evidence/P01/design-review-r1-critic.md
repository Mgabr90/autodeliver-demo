## Should-fix
- Design step 1 / R6 (limiter key) and the "reliable duplicate-email refusal" goal — The plan only trims spaces from the key. `UserStore` (`signup/store.py:19`) and `validate_email` (`signup/validator.py:20`) also match emails exactly as typed, so case counts. That means `Ana@Example.com` and `ana@example.com` each get their own account, which breaks the "one account per email" goal in HANDOFF.md. It also gets around the limiter: an attacker can change the case of letters to get unlimited buckets of 5 tries for the same mailbox. T8 only tests the exact same string, so the duplicate refusal is called "reliable" without proof. — The roadmap row's "reliable" refusal isn't delivered, and the limit is trivial to bypass. — Fix: rule on one normalisation (at least strip plus lower-case) used by both the store key and the limiter key. Add `signup/validator.py` and/or `signup/store.py` to the file boundary, and add a test that a case variant is refused as a duplicate and shares the limiter bucket.
- R4 (validation errors count as failures) together with `signup/validator.py:25` — The password check uses `len(password) <= MIN_PASSWORD_LENGTH`, so it rejects an 8-character password. SYSTEM.md and the error message both say 8 is the minimum. Under R4, a real user who enters a valid 8-character password gets refused 5 times and is then locked out for 15 minutes. The plan's Risks section says lockouts only happen when someone attacks a victim's email, but this lockout comes from the service's own defect. — Normal, honest use gets locked out, and the risk analysis rests on an untrue claim about how the system works now. — Fix: fix the off-by-one in this phase (boundary plus a test at exactly 8 characters) by a ruling that extends the boundary, or route it to the roadmap follow-ups with a ruling. Either way, update the lockout risk.
- Risks: "No new outside services. The mailer path is unchanged" (`signup/service.py:33-38`) — The current code sets `welcome_sent = True` after the mailer raises an exception, and also when no mailer is configured. That treats a notice that was never sent as sent, which breaks the charter's fail-safe rule and the "no silent failures" goal. HANDOFF says this is a Should-fix at the gate. The plan says the mailer path is safe without checking it. — The phase gate (whole-phase review) will raise it, which costs a round. — Fix: either set `welcome_sent` only after the mailer returns successfully, with tests for no mailer and for a mailer that raises (adding to the boundary by ruling), or log it as a roadmap follow-up with a ruling.
- Risks: "Memory growth" / R3 — Old timestamps are pruned only when the same key is used again, and the plan keeps keys that have an empty list. Every invalid email still records a failure under its own key (any string, including junk). So an attacker who sends distinct junk emails makes the dict grow without limit, and those keys are never touched again. "One entry per distinct key with recent failures" understates this: in practice it is one entry per distinct key ever seen. — Memory can be exhausted through the abuse path this phase is meant to harden. — Fix: delete a key when its pruned list is empty. Also rule on one of these: don't record failures for input that fails the email-shape check, cap the number of tracked keys, or sweep stale keys from time to time. Add a test for each choice.

## Nits
- Goal and why / R5 — The plan says repeated failed attempts "cost hashing work" and "fill logs", and R5 says a blocked call "costs no hashing". The code doesn't support this. Validation failures return before `store.add`, duplicates are refused before PBKDF2 (`store.py:19-22`), and failed sign-ups are never logged. Only successful sign-ups hash. Correct the rationale so later readers don't depend on it.
- Design: "a default `FailedAttemptLimiter()` when none is given" — Say explicitly that the default is built inside `__init__` (like `store or UserStore()`), not as a default argument value. A default argument would share one limiter across all service instances and leak state between tests.
- Concurrency — The limiter checks `is_blocked` and records the failure later, with no lock, so concurrent callers can get past `max_failures`. This is fine for a single-threaded demo, but one sentence in Risks would state that assumption.
